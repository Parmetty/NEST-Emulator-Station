# 决策记录

一条一句：**结论 / 理由 / 被否掉的方案**。只记录“以后可能会被质疑”的决定，不记录实现细节。

## D1 · 引擎用外部进程 + JSON 清单

**结论**：每个模拟器是一份 `resources/engines/<id>.json` 加一个外部进程，主进程只负责监管。

**理由**：Dolphin / Cemu 这类重引擎本来就不是 libretro 形态；系统模式必须走独立进程；引擎崩溃不能拖死 UI；
加一台主机 = 加一份 JSON，不碰 TypeScript。

**否掉**：libretro 内嵌（要维护原生 addon 与 ABI，且覆盖不了 Wii U）。

## D2 · 引擎分发走“探测优先 + 官方链接”

**结论**：先找已安装的引擎；找不到就给官方下载页，不把二进制打进安装包。

**理由**：Dolphin 是 GPL、Snes9x 非商业、Cemu 闭源，随包分发要逐个谈授权；镜像还有校验与版本风险。

**否掉**：应用内一键下载托管。

**后续变更**：D13 起 mGBA（MPL 2.0）与 ares（ISC）已随包内置（`resources/engines/`）；本条只约束 Dolphin / Cemu 等不随包的重引擎。

## D3 · Electron + React + TypeScript

**结论**：electron-vite 构建，渲染进程 contextIsolation 开、nodeIntegration 关，IPC 入参全量 zod 校验。

**理由**：UI 需要精细的排版与动画，Web 技术最快；主进程负责文件与进程，职责清晰。

**否掉**：Tauri（本机没有 Rust / MSVC，装工具链要几个 G，且当时误判 Electron 无法运行）。

## D4 · 先 JSON 存储，后换 SQLite

**结论**：`userData/library.json`，写入用临时文件 + rename 保证原子性；对外只暴露 `Store` 接口。

**理由**：P0/P1 的库量级只有几千条，JSON 可直接用文本编辑器排查，且没有原生模块的 ABI 与打包负担。

**代价**：全量重写整个文件；换成 SQLite 时只需换 `Store` 的实现。

## D5 · 首页四区布局

**结论**：全屏主机照片（灰度、褪色、模糊）+ 左上 logo + 左侧树状列表 + 右下信息卡，右上年份水印，左下年代标尺。

**理由**：整屏照片比“卡片墙”更有主机味；左侧固定导航保证手柄可导航；信息卡承载操作提示。

**变更史**：标尺最初只有任天堂一条线，后改为**跟随平台切换**；水印保持 5.5% 不透明度不做竖排。

## D6 · 鼠标与键盘双通道，进入前必须确认

**结论**：列表悬停/单击只做选择；进入必须按 A / 点「进入」/ 双击，并且一律先弹「注意！您即将进入 XXX」。

**理由**：悬停即选中已经容易误触，如果再“点一下就启动”，手柄和鼠标用户都会翻车。

## D7 · 不内置任何版权物

**结论**：没有 ROM、BIOS、NAND、密钥；系统模式只引导用户导入自己的 dump，并做前置体检。

**理由**：法律风险 + 分发风险；同时这也是“系统模式”诚实的边界。

## D8 · 用假引擎验证生命周期

**结论**：`tools/fake-engine.mjs` 模拟启动、崩溃、挂起、系统模式，测试与 CI 都不需要 ROM。

**理由**：没有 ROM 也能端到端验证进程监管；崩溃路径可以稳定复现。

## D9 · 环境适配：数据目录与启动器

**结论**：受限环境用 `--user-data-dir` 指到工作区（`npm run start:here`）；`tools/run.mjs` 启动前清掉
`ELECTRON_RUN_AS_NODE`。

**理由**：本机的沙箱不允许进程写 `%APPDATA%`，Electron 建数据目录失败会直接 `0xC0000005`；
另外全局设了 `ELECTRON_RUN_AS_NODE=1`，不清掉 electron 会当 node 跑。

**代价**：截图要走 `--shot`（`capturePage` + 静止帧），因为窗口未显示时合成器会节流。

## D10 · 扫描按内容哈希去重，DAT 匹配留到 P2

**结论**：`sha1` 前 16 位作游戏 id，扫描按哈希去重；标题先由文件名清洗得到。

**理由**：P1 要的是链路闭环，No-Intro/Redump 的 DAT 匹配属于准确性优化，放 P2；
按内容去重可以避免同一个 ROM 拖进两个文件夹后重复入库。

**否掉**：按路径去重（文件一移动就重复）。

## D11 · 游戏库是覆盖层，不是新页面

**结论**：按 A 进入主机后，游戏库以全屏覆盖层出现在首页之上，背景照片仍然在，只是被压暗模糊。

**理由**：保留“主机感”，返回成本低（B 一下回到原地）；也避免为每个系统维护一套路由。

**代价**：覆盖层打开时要隐藏首页的信息卡与时间线，否则会透过来干扰阅读。

## D12 · 系统模式按“是否真有系统”校正

**结论**：GBA 不再有「系统模式」入口；GameCube 加上「IPL 系统菜单」。

**理由**：GB/GBA 没有系统菜单，BIOS 只有一段开机动画，而且这段动画是每次开游戏都会走的，不是一个可进入的“系统”；
GameCube 确实有 IPL（Boot ROM）菜单，虽然少见但真实存在。3DS / NDS / Wii / Wii U 保留。

**影响**：`SYSTEMS` 里 `systemMode` 字段就是“真实性开关”，UI 的 `X` 键由它驱动。

## D13 · mGBA 直接随包内置

**结论**：`resources/engines/mgba/` 里放 mGBA 0.10.5 的完整运行时（41.5 MB），清单优先探测这个路径。

**理由**：mGBA 是 MPL 2.0，允许再分发；体积可接受；GBA 是第一个要“真的能玩”的主机，
让用户先去找引擎会毁掉“一站式”的承诺。Dolphin / Cemu 这类重引擎仍然只探测、不内置。

**代价**：安装包变大；升级引擎要跟着发版。`LICENSE.txt` 与 `licenses/` 原样保留。

## D14 · 启动时最小化主窗口（可关）

**结论**：默认开启，引擎退出后自动还原并聚焦；设置面板里可以关掉。

**理由**：模拟器窗口被 Nest 挡住是最扫兴的一步；但有人喜欢边上挂着列表，所以做成开关而不是硬编码。

## D15 · 封面用独立抓屏工具，而不是截图热键

**结论**：`resources/tools/nest-capture.exe` 常驻抓目标进程窗口的客户区，主进程在引擎退出时把最新一帧存为封面。

**理由**：
- 退出检测是精确的（子进程 `close` 事件），但窗口那时已销毁，所以必须“持续抓、退出时取最后一帧”。
- mGBA 的 F12 热键要求窗口处于激活状态，后台定时按会抢焦点，打断玩家。
- PowerShell 里 `Add-Type`（P/Invoke）在 Electron 子进程里会静默失败，无法复现；编译成独立 exe 后彻底消失。
- 客户区就是模拟器渲染的画面；再按主机比例从**底部**锚定裁剪，去掉 Qt 画在客户区里的菜单栏。

**否掉**：按亮度裁黑边（黑屏过场会被误裁）、按两帧差异裁（战斗过场等功能性黑边会被误判）。

**代价**：多一个二进制要构建（`npm run build:capture`，用系统自带 csc）；抓屏要求窗口可见，最小化时不抓。

## D16 · 从库中移除不删文件

**结论**：右键 →「从库中移除」只删 `library.json` 里的记录，磁盘上的 ROM 不动。

**理由**：误点一次就删掉用户 16MB 的游戏是不可接受的；要删文件让用户自己去资源管理器删。

## D17 · 单实例锁（来自分支版本的评审）

**结论**：用 `app.requestSingleInstanceLock()` 保证同一时刻只有一个 Nest 持有数据目录；第二实例只负责把已有窗口调到前台然后退出。

**理由**：`Nest.bat` 固定 `--user-data-dir=.profile`，没有锁时双击几次就有几个 Electron 抢同一个 Chromium 配置目录，部分实例会永远停在窗口出现之前——表现就是「Nest 有时候打不开」。分支版本的作者在同一台机器上清理出过 36 个无窗口的残留进程，根因就是这个。

**实现细节**：`--smoke` / `--shot=` / `--trylaunch=` 等自动化标志会跳过锁，否则残留窗口会挡住测试；锁没拿到时 `boot()` 不执行，避免两个实例同时写库。

## D18 · 窗口立即显示，`ready-to-show` 只用来聚焦

**结论**：`show: true`，不再隐藏窗口等 `ready-to-show`。

**理由**：杀毒软件扫描渲染包时 `ready-to-show` 能拖好几秒，用户看到的是「双击了没反应」。窗口底色是 `#08080a`，先出现一个深色窗口比什么都不出现更可信。

**代价**：首帧绘制前可能看到零点几秒的纯色窗口；截图流程（`--shot`）仍在 `did-finish-load` 后加 `.still` 再抓，不受影响。




## D19 · 系统模式：能走命令行就不碰 GUI（Dolphin / NGC + Wii）

**结论**：引擎若只能用图形界面进入系统模式，就在清单里用 `systemBoot` 描述一段按键序列，
由 `resources/tools/nest-input.exe` 在窗口出现后置前并发送，Nest 不嵌入 UI 自动化框架。

**理由**：Dolphin 的 CLI 明确只接受 GCM/ISO（`-e`），`-b` 还要求 `--exec`/`--nand-title`；
「载入 GameCube 主菜单」是纯 GUI 动作。与其给 Dolphin 打补丁，不如把“已知版本的已知按键序列”写成数据。

**代价与边界**：
- 序列绑死 Dolphin 版本与界面语言（我们随包固定 2609a；若改界面语言，助记键可能变）
- 只在 system 模式下触发，且失败不影响直读
- 若 Dolphin 将来提供命令行入口，`systemBoot` 直接删掉即可
**后续变更（Wii）**：Dolphin 可以直接把 System Menu 的 WAD 当启动目标——-b -e <wii-menu.wad> 即可进 Wii 菜单，完全静默、零打扰，比 GC 那条路干净得多。因此清单新增 systemArgsBySystem：Wii 走 WAD 直启，GC 保留 UIA 菜单（实验性）。

**UIA 的副作用（实测）**：Qt 菜单展开的瞬间会抓鼠标/键盘，用户此时操作会感到被抢。助手已改为单次尝试、异常不外泄、失败必收起菜单；但根本上这是 GUI 自动化，NGC 的入口标注为实验性，直到 Dolphin 提供命令行入口。
**后续变更（NGC 暂停）**：UIA 实测又慢又不可靠（Qt 菜单展开会抢占输入），NGC 的 `systemMode` 入口已从 `systems.ts` 撤掉。直读不受影响：Nest 每次启动前把 Dolphin 的 `SkipIPL` 设为 True，所以不需要 IPL；只有当用户真的想进 GC 主菜单时才需要 IPL，而那条路要等 Dolphin 提供命令行入口（或我们魔改构建）。

## D20 · 只发免安装携带版，不做安装程序

**结论**：不发布 NSIS 安装包，只提供 `Nest-0.3.0-portable.zip`（解压后双击 `启动 Nest.bat` 即用）。

**理由**：
- 体量小、更新频繁：234 MB 的 zip 直接覆盖解压即可，安装包反而多一层卸载残留
- 主要在熟人之间传，不需要注册表、开始菜单、控制面板卸载项
- 免安装版天然支持多份并存（不同版本各放一个文件夹），调试时更省事

**实现**：`启动 Nest.bat` 用 `--user-data-dir="%~dp0data"` 启动，库 / 封面 / 日志 / 引擎配置都留在解压目录；删掉 `data` 即恢复出厂。
**教训**：不要试图在运行期改 Chromium 的 userData 路径——`app.setPath` 与「重启自身」两种写法都让打包版进程崩溃（0xC0000005 / 0x80000003），已全部放弃。

**代价**：
- 无法在资源管理器里点「卸载」清理（删文件夹即可，但 `%APPDATA%` 下若有旧数据需手动删）
- 用户拿到的是一堆文件夹，可能误删 `resources` 导致引擎消失

**后续**：若将来加自动更新或需要写系统目录，再回头做安装版；NSIS 配置（`oneClick:false` + `allowToChangeInstallationDirectory:true`）已留在 `package.json` 里备查。

## D21 · ares 键盘绑定格式（2026-10-30 实验破译）

**结论**：ares 的 `settings.bml` 里，输入绑定写成

```
0x<deviceID>/<groupID>/<inputID hex>;;
```

键盘是 `0x1/0/<VK码>;;`；`inputID` 是 **Windows 虚拟键码（VK）的十六进制**，不是 SDL scancode。
空绑定写 `;;`。

**证据**：
- 在 ares v148 里手动把 Famicom 的 Up 绑到 W，ares 自己写出 `Up: 0x1/0/57;;`（0x57 = VK_W）
- 反向验证：把 `Up: ;;` 改成 `Up: 0x1/0/57;;` 后启动 ares → Settings → Input，Up 行显示「键盘图标 + W」，说明解析与设备解析都正确
- 此前失败的两个候选：`Keyboard/0/40`（3 段，被 input.cpp 忽略）、`0x0/0/40`（设备号错，且 40 是 SDL scancode 而非 VK）

**实现**：`src/main/controls/ares.ts` + `keymap.ts` 的 VK 表；写入 Famicom / FamicomDiskSystem / SuperFamicom / Nintendo64 的 `Input → Controller.Port.1 → Gamepad`。

**风险**：设备号 `0x1` 是 ares 运行时枚举出的 id，本机可复现；若某台机器键盘枚举顺序不同，绑定会显示 `(disconnected)`。缓解：写入前检测失败就只写数字形式，并在日志里提示；后续可改用 identifier 形式（需再实验确认键盘 identifier 字符串）。

### D21 实测对照（2026-10-30，ares v148）

| 动作 | 用户按的键 | ares 自己写的值 | 我们的 VK 推导值 | 界面显示 |
|---|---|---|---|---|
| Up | W | `0x1/0/57;;` | `0x1/0/57;;` | W ✅ |
| Down | S | `0x1/0/53;;` | `0x1/0/53;;` | S ✅ |
| Left | A | `0x1/0/35;;` | `0x1/0/41;;` | G ❌ |
| Right | D | `0x1/0/38;;` | `0x1/0/44;;` | J ❌ |
| A 键 | J | `0x1/0/44;;` | `0x1/0/4a;;` | F4 ❌ |
| B 键 | K | `0x1/0/45;;` | `0x1/0/4b;;` | F4 ❌ |
| Start | Enter | `0x1/0/91;;` | `0x1/0/d;;` | Escape ❌（手动改后有效） |

结论：inputID 不是 Windows VK（W/S 只是巧合相同），更像 ares/ruby 自己的键盘枚举索引。
下一步需要从 ruby/hiro 源码拿键盘 input 表，或让用户再绑一组键做对照（每绑一个键记下键名），
在拿到确定映射前不自动写，避免生成“看似配置好但按了没反应”的 layouts。

### D21 最终修正（2026-10-30，源码确认）

**结论**：`0x1/0/<id>;;` 的 `<id>` 是**十进制**的 ruby Windows 键盘表下标（`ruby/input/keyboard/rawinput.cpp` 的 `keys[]` 顺序），
不是 VK、不是 scancode、也不是十六进制。完整依据与 102 项对照表见 `docs/KEYS-ARES-FORMAT.md`。

关键点：
- 设备 `0x1` = `(pathID<<32)|(vendorID<<16)|productID`，键盘用写死的 GenericVendor/ProductID(0x0000/0x0001) → **跨机器稳定**
- `groupID` 恒为 `0`（键盘只有 Button 组）
- ares 的 `natural()` 是十进制解析，`4a` 会被读成 `4`、`d` 读成 `0` —— 这正是旧 VK 方案只对 W/S 有效的原因
- `;;` 是「3 个 mapping 槽用 `;` 拼接后去掉一个尾分隔符」的产物；裸写 `0x1/0/57` 也能解析

据此已恢复 ares 自动写入，`docs/KEYS-ARES.md` 与测试同步更新。
